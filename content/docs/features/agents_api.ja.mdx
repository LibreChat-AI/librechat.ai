<Callout type="warning" title="ベータ機能">
Agents APIは現在ベータ版です。安定版リリースに向けて開発を進める中で、endpoint、リクエスト/レスポンスの形式、および動作が変更される可能性があります。
</Callout>

LibreChatは、推論APIおよびイベント配信APIを通じて、エージェントを外部アプリケーション、スクリプト、およびサービスに公開します。

## 概要 [#overview]

Agents APIは、2つの推論インターフェースと認証済みイベント配信を提供します：

- **OpenAI互換のChat Completions** — `POST /api/agents/v1/chat/completions`
- **Open Responses API** — `POST /api/agents/v1/responses`
- **エージェントイベント** — `POST /api/agents/v1/events`

推論インターフェースは、APIキー認証、オプションのOIDC認証、およびストリーミングレスポンスをサポートしています。Agent EventsはRemote AgentsのAPIキー認証を使用するため、LibreChatは各配信を安定したソースIDに紐付けることができます。

LibreChatは、エージェントを提供するための主要なAPIフレームワークとして[Open Responses](https://www.openresponses.org/)を採用しています。Chat Completions endpointは既存のOpenAI互換ツールとの後方互換性を提供しますが、Open Responses endpointは将来の方向性を表しています。

## Agents API を有効にする [#enabling-the-agents-api]

Agents APIは、`remoteAgents`インターフェース設定によって制限されています。すべての権限はデフォルトで`false`に設定されています。

```yaml filename="librechat.yaml"
interface:
  remoteAgents:
    use: true
    create: true
```

利用可能なすべてのオプションについては、[Interface Configuration — remoteAgents](/docs/configuration/librechat_yaml/object_structure/interface#remoteagents) を参照してください。

**注:** 管理者ユーザーには、すべてのリモートエージェント権限がデフォルトで有効になっています。

## API Key Management [#api-key-management]

`remoteAgents.use` および `remoteAgents.create` が有効になると、ユーザーは LibreChat UI から API キーを生成できるようになります。これらのキーは、Agents API へのリクエストを認証するために使用されます。

## 認証 [#authentication]

Agents APIは、個別または組み合わせて使用できる2つの認証方法をサポートしています。

### API Key [#api-key]

APIキー認証はデフォルトで有効になっています。`remoteAgents.use` および `remoteAgents.create` が有効になったら、LibreChat UIからAPIキーを生成してください。

```bash
Authorization: Bearer <YOUR_API_KEY>
```

### OIDC Bearer Token [#oidc-bearer-token]

インフラストラクチャにすでにOIDCプロバイダーが存在するマシン間（M2M）のシナリオでは、LibreChat APIキーを使用せずに、OIDC Bearerトークンで直接認証を行うことができます。

`librechat.yaml` で OIDC 認証を設定します:

```yaml filename="librechat.yaml"
endpoints:
  agents:
    remoteApi:
      auth:
        apiKey:
          enabled: false
        oidc:
          enabled: true
          issuer: https://auth.example.com/realms/myrealm
          # jwksUri is optional and auto-discovered from issuer if omitted
          audience: my-client-id
```

次に、OIDCアクセストークンを使用してAPIを呼び出します：

```bash
curl -X POST https://your-librechat-instance/api/agents/v1/responses \
  -H "Authorization: Bearer YOUR_OIDC_ACCESS_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"model": "agent_abc123", "input": "Hello!"}'
```

<Callout type="info">
  OIDCトークンは、LibreChatに既に存在するユーザーのものである必要があります。照合にはまず `sub` クレームが使用され、次に `email`、`preferred_username`、または `upn` が順次フォールバックとして使用されます。
</Callout>

すべての設定オプションについては、[Agents Endpoint - remoteApi](/docs/configuration/librechat_yaml/object_structure/agents#remoteapi) を参照してください。

<Callout type="warning" title="Agent EventsにはAPIキーが必要です">
  Agent Events エンドポイントでは、OIDC のみの認証はサポートされていません。バインディングの作成、イベントのエンキュー、および配信ステータスのポーリングを行う際は、Remote Agents API キーを使用してください。
</Callout>

## Endpoints [#endpoints]

### Chat Completions (OpenAI互換) [#chat-completions-openai-compatible]

```
POST /api/agents/v1/chat/completions
```

LibreChat インスタンスを指定することで、あらゆる OpenAI 互換 SDK を使用できます。`model` パラメータはエージェント ID に対応しています。

**curlを使用した例:**
```bash
curl -X POST https://your-librechat-instance/api/agents/v1/chat/completions \
  -H "Authorization: Bearer YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "agent_abc123",
    "messages": [
      {"role": "user", "content": "Hello, what can you help me with?"}
    ],
    "stream": true
  }'
```

**OpenAI SDK (Python) を使用した例:**
```python
from openai import OpenAI

client = OpenAI(
    base_url="https://your-librechat-instance/api/agents/v1",
    api_key="YOUR_API_KEY"
)

response = client.chat.completions.create(
    model="agent_abc123",
    messages=[{"role": "user", "content": "Hello!"}],
    stream=True
)

for chunk in response:
    print(chunk.choices[0].delta.content, end="")
```

### モデルの一覧表示 [#list-models]

```
GET /api/agents/v1/models
```

利用可能なエージェントをモデルとして返します。APIキーでどのアージェントにアクセスできるかを確認するのに便利です。

### Open Responses API [#open-responses-api]

```
POST /api/agents/v1/responses
```

Open Responses endpointは、OpenAIが主導し、オープンソースAIコミュニティによって構築されたオープン推論標準である[Open Responses specification](https://www.openresponses.org/)に従っています。これは、推論、ツール使用、構造化出力、およびストリーミングセマンティックイベントをネイティブでサポートする、エージェントワークフロー向けに設計されています。

```bash
curl -X POST https://your-librechat-instance/api/agents/v1/responses \
  -H "Authorization: Bearer YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "agent_abc123",
    "input": "What is the weather today?"
  }'
```

## Agent Events [#agent-events]

Agent Eventsを使用すると、認証されたコントローラーまたはソースアダプターが、Agentに対して永続的な作業を配信できるようになります。イベント配信はベータ版の機能であり、そのリクエスト、レスポンス、およびランタイムの動作は変更される可能性があります。

各endpointは、認証されたユーザー、テナント、およびAPIキーを使用します。ターゲットとなるAgentは、既存のRemote Agentsの権限設定において、そのユーザーから参照可能である必要があります。Agent Eventのリクエストには、専用の [`rateLimits.agentEvents`](/docs/configuration/librechat_yaml/object_structure/config#ratelimits) バケットも使用されます。

### イベントを配信する [#deliver-an-event]

```http
POST /api/agents/v1/events
Authorization: Bearer <REMOTE_AGENTS_API_KEY>
Idempotency-Key: webhook-42-resource-7
Content-Type: application/json

{
  "mode": "fire",
  "event": {
    "id": "resource-7-ready-3",
    "type": "resource.ready",
    "occurredAt": 1786967999000,
    "payload": { "resourceId": "resource-7" }
  },
  "target": { "agentId": "agent_abc123" },
  "input": "Resource resource-7 is ready. Inspect it and report the result.",
  "orderingKey": "resource-7"
}
```

`Idempotency-Key` ヘッダーを正確に1つ送信し、同じソースイベントからターゲットへの配信を再試行する際にはそのキーを再利用してください。キーには1〜256文字の英数字、または `._~:/+=-` の文字を含める必要があります。異なる配信内容でキーを再利用すると、競合が返されます。

呼び出し元はイベントの `id`、`type`、`occurredAt`、およびサニタイズされた `payload` を提供します。LibreChat は呼び出し元が提供した `event.source` を認証済み API キーのアイデンティティに置き換え、ユーザー、テナント、リクエスト ID、および受信時刻を導出します。受け入れられた配信は永続化されるため、イベントのペイロードに認証情報や転送用のシークレットを含めないでください。

`orderingKey` はオプションです。異なるソースからの配信を同じリソースに対して順序立てる必要がある場合は、固定の値を使用してください。

リクエストが成功すると、`202 Accepted`、不透明な配信 `id`、現在のステータス、および `Location` ヘッダーが返されます。その場所をポーリングしてください：

```http
GET /api/agents/v1/events/{delivery_id}
Authorization: Bearer <SAME_REMOTE_AGENTS_API_KEY>
```

配信は `pending`、`leased`、`succeeded`、または `dead` のいずれかになります。ステータスレスポンスには、試行回数とタイムスタンプに加え、完了時の結果またはパブリックエラーが含まれます。保存されたペイロード、順序付けキー、再試行履歴、またはワーカーIDは公開されません。ステータスへのアクセスは、同一のユーザー、テナント、および API キーソースに限定されます。

バインドされた `continue` の場合、`succeeded` はエージェントのターンが許可されたことを意味し、要求された作業が完了したことを意味するわけではありません。したがって、そのステータスは、`started` に続き、`applied`、`completed_no_action`、`failed`、または `cancelled` のいずれか1つが必ず発生する、永続的な `handling` ライフサイクルも公開します。

アクション対応のソースには、ツール名とオプションの引数サブセットを含む `expectedAction` を含めることができます。LibreChat は、その正確な生成がホスト側で観測されたツールエビデンスと契約内容に一致して完了した場合にのみ `applied` を報告します。モデルが作成した文章は、証拠として決して受け入れられません。`fire`、`steer`、およびバインドされていない `continue` の配信は、`expectedAction` を拒否します。

`fire` が成功すると、その後の `steer` イベントでターゲットにできる会話と生成の識別情報が返されます。

### イベント駆動型の子エージェント [#event-driven-child-agents]

外部システムは、ソースアクターを直接の子Agentにバインドし、その後同じ子会話をイベント間で継続させることができます。バインドされた子継続は、APIキーのID、バインドの所有権、親子関係、およびAgentの承認チェックが成功した後に自動的に行われます。これには個別の機能トグルは存在しません。

その後のターンを配信するのと同じAPIキーを使用してアクターを登録します：

```http
POST /api/agents/v1/events/bindings
Authorization: Bearer <REMOTE_AGENTS_API_KEY>
Idempotency-Key: championship-7-player-hanae
Content-Type: application/json

{
  "actorId": "hanae-kobayashi",
  "parentConversationId": "director-conversation-id",
  "parentMessageId": "director-message-id",
  "target": { "agentId": "agent_hanae" }
}
```

`actorId` は最大128文字まで含めることができます。親は通常の Agent 会話である必要があり、ターゲットはその Agent の直接の Subagent、または許可された自己生成（self-spawn）として構成されている必要があります。新しいバインディングは `201` を返し、べき等なリプレイは `200` を返します。どちらのレスポンスにも `id`、`actorId`、`agentId`、および `threadId` が含まれます。

返されたバインディングIDを使用して、以降のターンを送信します：

```http
POST /api/agents/v1/events
Authorization: Bearer <SAME_REMOTE_AGENTS_API_KEY>
Idempotency-Key: game-12-ply-17-hanae
Content-Type: application/json

{
  "mode": "continue",
  "bindingId": "evtbind_...",
  "event": {
    "id": "game-12-ply-17",
    "type": "chess.turn.ready",
    "occurredAt": 1786968000000,
    "payload": { "gameId": "game-12", "expectedPly": 17 }
  },
  "input": "Your clock is running. Read the position and submit one legal move.",
  "expectedAction": {
    "tool": "submit_move",
    "arguments": { "gameId": "game-12" }
  }
}
```

LibreChatは、ディスパッチの直前に、バインディングから子Agent、スレッド、最新のブランチリーフ、および順序付けレーンを解決します。呼び出し元が提供したターゲットおよび順序付けフィールドは、バインドされた継続をリダイレクトすることはできません。リクエストの `Idempotency-Key` は、配信の再試行、生成リーシング、永続化されたメッセージ、ライブアクティビティ、およびその後のHITL再開全体にわたって、その子ターンの安定した公開IDとなります。

各バインディングには自動的な永続メールボックスがあります。次のイベントは、現在のターンが `applied`、`completed_no_action`、`failed`、または `cancelled` に達するまでキューに入れられたままになります。異なるバインディングは独立しており、並行して実行可能です。チェックポイントの継続は、互換性のある初期化済みターンに対してのみ試行されます。チェックポイントが存在しないか復元できない場合、LibreChatは受信、承認、または期待されるアクションのチェックを弱めることなく、永続的なメッセージ履歴にフォールバックします。

バインドされたアクターは、「Ask User（ユーザーへの問い合わせ）」またはツール承認のために一時停止できます。LibreChatは、保留中のアクションを公開する前に正確な署名済みサスペンションを永続化し、そのアクターの呼び出しが再開または解決されるまで、バインディングのメールボックスはブロックされたままになります。Event Actorsには永続的なMongoDBチェックポインターが必要であり、`type: memory` は互換性がありません。LibreChatは生成プロトコルv2をネゴシエートし、チェックポイントまたは履歴の継続を自動的に選択します。既存のプロトコルv1の作業は、完了するまで永続的な履歴パスに残ります。混在バージョンのデプロイ要件については、[Generation Protocol Compatibility](/docs/configuration/redis#generation-protocol-compatibility) を参照してください。

### 観測イベントの統合 (Coalescing Observational Events) [#coalescing-observational-events]

複数の `continue` イベントが互換性のある観測結果であることを証明できるソースには、同じソース定義の `coalesce.key` を付与することができます。

```json
{
  "mode": "continue",
  "bindingId": "evtbind_...",
  "event": {
    "id": "championship-7-game-12-move-18",
    "type": "chess.move.completed",
    "occurredAt": 1786968000750,
    "payload": { "gameId": "game-12", "ply": 18 }
  },
  "input": "A tournament game advanced.",
  "coalesce": { "key": "championship-commentary" }
}
```

LibreChatは、最大750ミリ秒間、最大8件のイベント、および合計512 KiBのエンベロープまで、互換性のあるイベントを収集します。子プロセスは1つの決定論的なバッチドキュメントを受け取りますが、各ソースイベントは独自の `Idempotency-Key`、配信記録、およびレシートを保持します。

アクションを伴わない観測に対してのみ、コアレッシング（coalescing）を使用してください。`fire`、`steer`、バインドされていない`continue`、および`expectedAction`を伴う配信に対しては拒否されます。コマンド、承認、HITLリクエスト、フェンス、または個別のタイミングが重要なイベントには使用しないでください。

認証済みの親会話では、各バインドされたアクターは、それを所有する親メッセージの下に表示されます。Subagentパネルでは、アクターとターンの切り替え、過去のアクティビティの読み込み、ターンの展開によるバインドされた全アクティビティの表示が可能です。イベントの詳細には、タイプ、ソース、発生時刻、期待されるアクションが含まれます。表示可能な実行ステップ、ツール、メッセージ、推論マーカーは含まれますが、生の推論テキストは含まれません。親インデックスは、バインドされたソースウィンドウから最大64個の子スレッドと、子ごとに最大20個の最近のタスクを返し、完全であることを示唆するのではなく切り捨てを報告し、応答を96 KBに制限します。これは親、ユーザー、およびテナントによって認証されており、バインド、ソースキーID、リース・トークン、およびワーカーの状態はプロジェクションに含まれません。

子スレッドは通常の会話ナビゲーションからは非表示となり、人間によるチャットルートからは読み取り専用となります。また、親スレッドの一時的または有効期限ポリシーを継承し、直接の子レベルは1つまでに制限されます。バインディングID単体ではアクセス権は付与されません。継続（continuations）は、それを作成したユーザー、テナント、およびAPIキーのスコープ内に限定されます。

### 分離されたイベントアクターアクション [#detached-event-actor-actions]

Event Actorのターンは、対象となるActionを切り離し、永続的に完了させることができます。Actionの実行中、配信はその処理ライフサイクル内に留まります。永続的な最終エビデンスが元の署名済みActor呼び出しを再開させ、ホストが観測した結果のツールエビデンスのみが `expectedAction` を満たすことができます。リプレイや競合するレプリカが、同じ予約済みActionを二度起動することはできません。LibreChatが外部の副作用が開始されたかどうかを判断できない場合、盲目的に再試行するのではなく、その起動を隔離（quarantine）します。

LibreChatは、選択された組み込み生成ストアがサポートを通知すると、この内部補完作業を自動的に有効にします。インメモリ・ストアは、起動、補完、および継続を単一のプロセスで実行するため、プロセス終了後にその作業を復旧することはできません。Redis生成ストリームを追加すると、永続的な再起動復旧とレプリカのハンドオフが可能になります。機能が所有する配信および復旧レコードは、バージョンが混在するドレイン（排出）中、古いクレイマーからは不可視のままとなります。オペレーターが管理するプロデューサーフラグは存在しません。

## トークン使用量の追跡 [#token-usage-tracking]

すべてのAgents API推論リクエストは、トークン消費が設定されている場合、ユーザーの残高に対してトークン使用量を追跡します。ストリーミングおよび非ストリーミングの両方のレスポンスにおいて、課金対象となるすべてのプライマリAgentおよびSubagentのモデル呼び出しが、最上位の合計値に集計されます。レスポンスには、IDを含まない`primary`および`subagent`のトークン内訳も含まれます。プロバイダーが報告する場合、キャッシュおよび推論トークンの詳細も含まれます。
