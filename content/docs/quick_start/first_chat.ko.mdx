LibreChat은 직접 호스팅하는 소프트웨어이며, 자체 API 키를 포함하고 있지 않습니다. 인스턴스가 실행되면 다음 단계를 통해 로그인 페이지에서 대화가 가능한 상태로 전환할 수 있습니다.

<Callout type="info" title="아직 실행 중인 것이 없나요?">

먼저 LibreChat을 설치하세요: 5분 만에 완료하는 Docker 경로는 [Quick Start](/docs/quick_start)를, Docker, npm 또는 Helm을 이용한 설치는 [Local Installation](/docs/local)을, 서버에 배포하려면 [Remote Hosting](/docs/remote)을 참조하세요.

아무것도 설치하지 않고 LibreChat을 체험해 보려면, 프로젝트에서 운영하는 무료 공개 데모인 [chat.librechat.ai](https://chat.librechat.ai)를 이용해 보세요. 이는 평가용이며, 개인 데이터용이 아닙니다.

</Callout>

  <Step>

### 브라우저에서 LibreChat 열기 [#open-librechat-in-your-browser]

로컬 Docker 또는 npm 설치는 [http://localhost:3080](http://localhost:3080)에서 앱을 제공합니다. 포트는 `PORT`에서 가져옵니다. 만약 이를 변경했거나 `docker-compose.override.yml`에서 다른 호스트 포트를 매핑했다면, 해당 포트를 대신 사용하세요.

그 외의 경우, 주소는 배포 환경에서 제공하는 주소입니다. Railway가 할당한 도메인, Hugging Face의 `username-projectname.hf.space` URL, 또는 원격 Docker나 Kubernetes 설치 앞에 있는 서버 IP나 도메인이 이에 해당합니다. `DOMAIN_CLIENT`는 별도의 설정으로, LibreChat이 생성하는 링크에 포함되는 주소입니다. 따라서 브라우저 주소창의 주소를 그대로 읽어오기보다는 해당 공개 URL을 가리키도록 설정하십시오.

아무것도 로드되지 않으면 아래의 [If nothing loads](#if-nothing-loads)를 참조하세요.

  </Step>
  <Step>

### 계정 생성 [#create-your-account]

이메일 등록은 기본적으로 활성화되어 있으며(`ALLOW_REGISTRATION=true`), 기본 자격 증명은 없습니다. **Sign up**을 클릭하고 원하는 이메일과 비밀번호를 선택하세요.

모든 인스턴스가 해당 양식을 제공하는 것은 아닙니다. **Sign up**이 없다면 제공된 경우 공급자 버튼을 사용하거나, 인스턴스가 디렉터리에 대해 인증하는 경우 로그인 양식을 사용하세요. 둘 중 하나를 통해 첫 로그인 시 계정이 생성될 수 있습니다. 제공되는 옵션이 없거나 계정이 존재하지 않아 로그인이 거부되는 경우, 인스턴스 관리자에게 계정을 요청하세요. 어떤 컨트롤이 표시되는지는 인스턴스의 [authentication settings](/docs/configuration/authentication)에 의해 결정됩니다.

<Callout type="info" title="단일 테넌트 배포에서 첫 번째 계정 = 관리자">

범위가 지정되지 않은 단일 테넌트 배포에서는 처음 등록된 계정이 관리자 계정이 되며, 그 이후의 모든 계정은 기본적으로 `USER` 역할을 부여받습니다. 테넌트 범위가 지정된 배포에서는 각 테넌트의 첫 번째 사용자를 자동으로 승격하지 않습니다. 신뢰할 수 있는 관리 흐름([Authentication](/docs/features/authentication))을 통해 테넌트 관리자를 프로비저닝하십시오.

OpenID 배포는 기본 역할을 양방향으로 재정의할 수 있습니다. `OPENID_ADMIN_ROLE`은 일치하는 계정을 관리자로 승격시키며, 일반 역할 동기화(`OPENID_ROLE_SYNC_ENABLED`)는 공급자 역할을 다른 비관리자 역할에 매핑합니다. [OpenID Connect](/docs/configuration/dotenv#openid-connect)를 참조하세요.

</Callout>

[OAuth2/OIDC](/docs/configuration/authentication/OAuth2-OIDC) 또는 [SAML](/docs/configuration/authentication/SAML)을 구성한 경우, 양식 대신 해당 제공업체의 버튼을 사용하세요.

[LDAP/AD](/docs/configuration/authentication/ldap)는 별도의 버튼을 추가하지 않습니다. 서버에서 `LDAP_LOGIN_USES_USERNAME=true`로 설정된 경우, 이메일 대신 디렉토리 사용자 이름을 입력하여 동일한 이메일 및 비밀번호 양식으로 로그인하십시오.

  </Step>
  <Step>

### 모델에 API 키 부여하기 [#give-a-model-an-api-key]

LibreChat은 귀하의 자격 증명을 사용하여 AI 제공업체와 통신하며, `.env.example`은 미리 구성된 제공업체를 `user_provided`로 제공합니다:

```bash filename=".env"
OPENAI_API_KEY=user_provided
ANTHROPIC_API_KEY=user_provided
GOOGLE_KEY=user_provided
```

해당 값을 설정하면 모든 사용자가 웹 UI에서 직접 자신의 키를 입력하게 됩니다: 엔드포인트를 선택하고 옆에 있는 톱니바퀴 아이콘을 연 다음, **Set API Key** 대화 상자에 키를 입력하세요.

해당 값은 `.env.example`에서 설치를 시작하는 경우(즉, Docker 및 npm)에만 기본값으로 적용됩니다. Helm 릴리스, Railway 서비스 또는 Hugging Face Space는 사용자가 설정한 변수만 포함하므로, 자격 증명을 설정하지 않은 endpoint는 아예 로드되지 않으며 해당 endpoint에 대한 키 대화 상자도 나타나지 않습니다. 사용자가 직접 키를 가져오도록 하려면 해당 환경에서 변수를 `user_provided`로 설정한 다음, 실행 중인 pod나 컨테이너가 이를 반영할 수 있도록 워크로드를 다시 시작(roll)해야 합니다. 동일한 대화 상자는 **Settings → Data & Privacy → API keys**에서도 접근할 수 있으며, 이곳에서 나중에 키를 검토하고 교체할 수도 있습니다.

엔드포인트 드롭다운이나 톱니바퀴 아이콘이 보이지 않는다면, 해당 인스턴스는 [model specs](/docs/configuration/librechat_yaml/object_structure/model_specs) 또는 `interface` 설정을 통해 선택기를 숨겨둔 상태입니다. **설정(Settings) → 데이터 및 개인정보 보호(Data & Privacy) → API 키(API keys)**에서 첫 번째 키를 설정하세요. 이곳에는 사용자 제공 키를 사용하도록 구성된 엔드포인트 목록이 표시됩니다.

대신 모든 사용자를 위해 키를 한 번에 구성하려면 `user_provided` 대신 실제 키를 설정하고 LibreChat을 재시작하세요. Docker의 경우, 스택이 실행되는 파일에 따라 `-f ./deploy-compose.yml`을 추가하여 `docker compose up -d` 명령어로 컨테이너를 다시 생성하세요. `docker compose restart`는 컨테이너가 이미 가지고 있는 환경 변수를 유지하므로 이전 값이 그대로 남게 됩니다. 사용자에게는 아무런 메시지도 표시되지 않으며, 키는 서버에 유지됩니다. 설정 위치는 설치 방식에 따라 다릅니다: Docker 및 npm의 경우 `.env`, [Helm](/docs/local/helm_chart#configuration)의 경우 Kubernetes Secret, Railway 대시보드의 서비스 변수, [Hugging Face](/docs/remote/huggingface)의 경우 Space Secrets를 사용합니다. 공급자별 단계는 [AI Setup](/docs/configuration/pre_configured_ai)에서 확인할 수 있습니다.

<Callout type="warn" title="공개 URL에 있는 공유 키는 누구든지 사용할 수 있습니다">

등록은 기본적으로 열려 있으므로, 인터넷에서 접근 가능한 인스턴스의 경우 URL을 찾는 사람은 누구나 가입하여 귀하의 키로 비용을 청구할 수 있습니다. 공개 배포 환경에서 서버 측 키를 구성하기 전에 의도하지 않은 사람이 계정을 생성할 수 없도록 확인하십시오. 이메일 양식, 각 제공업체 버튼 및 인증에 사용하는 모든 디렉토리는 각자의 방식으로 사용자를 생성하므로, 하나를 닫는다고 해서 모두 닫히는 것은 아닙니다. [Authentication](/docs/configuration/authentication)에서 각 설정에 대해 다룹니다. 제공업체를 `user_provided`로 두면 이 문제를 완전히 방지할 수 있습니다.

</Callout>

<Callout type="info" title="유료 API 키가 없으신가요?">

[Ollama](/docs/configuration/librechat_yaml/ai_endpoints/ollama)를 사용하여 자신의 하드웨어에서 모델을 실행하거나, [OpenRouter](/docs/configuration/librechat_yaml/ai_endpoints/openrouter)와 같은 게이트웨이를 통해 여러 제공업체에 연결할 수 있습니다. 두 방식 모두 [custom endpoints](/docs/quick_start/custom_endpoints)로 추가됩니다.

</Callout>

  </Step>
  <Step>

### 첫 메시지 보내기 [#send-your-first-message]

채팅 상단의 선택기에서 endpoint와 모델을 선택하고, 프롬프트를 입력한 뒤 전송하세요. 인스턴스에서 선택기가 숨겨져 있는 경우, 이미 설정이 완료된 상태이므로 바로 입력하고 전송하면 됩니다. 응답이 스트리밍 방식으로 출력되며, 대화가 저장되므로 사이드바에서 언제든지 다시 돌아올 수 있습니다.

  </Step>

## 아무것도 로드되지 않는 경우 [#if-nothing-loads]

페이지가 나타나지 않는 것은 설치 문제이며, 확인 방법은 설치 방식에 따라 다릅니다:

- **Docker.** `docker compose ps` 명령어로 컨테이너가 실행 중인지 확인한 다음, `docker compose logs api` 명령어로 API 로그를 읽습니다. [Docker on Linux](/docs/remote/docker_linux) 가이드에 따라 설정된 서버에서는 스택이 기본값이 아닌 compose 파일에서 실행되므로, `sudo docker compose -f ./deploy-compose.yml ps` 및 `sudo docker compose -f ./deploy-compose.yml logs api`를 사용하세요. 자세한 내용은 [Docker troubleshooting](/docs/local/docker#troubleshooting)에서 확인할 수 있습니다.
- **npm.** LibreChat은 `npm run backend`를 시작한 터미널에서 실행되므로, 해당 터미널의 출력을 확인하세요. 프로세스가 종료되었다면 다시 시작하여 출력되는 오류를 확인하세요.
- **[Helm](/docs/local/helm_chart) 또는 다른 Kubernetes 설치.** `kubectl get pods -n <release-namespace>`를 사용하여 파드가 실행 중인지 확인하고, `kubectl logs -n <release-namespace> <pod>`로 API 파드 로그를 읽으며, 서비스나 인그레스가 실제로 브라우징 중인 포트를 노출하고 있는지 확인하세요. 두 명령어 모두 현재 네임스페이스를 기본값으로 사용하므로, 목록이 비어 있다면 대개 잘못된 네임스페이스를 사용 중인 것입니다.
- **Railway 또는 기타 호스트.** 제공업체의 대시보드에서 배포 로그를 열고(Railway의 경우 서비스의 **View logs** 버튼), `localhost` 대신 제공업체가 할당한 공용 URL로 이동하세요.

## 모델이 답변하지 않는 경우 [#if-no-model-answers]

- **선택기에서 endpoint 자체가 누락된 경우.** 세 가지 개별 설정이 이를 숨길 수 있으므로 각각 확인해야 합니다. `.env`의 `ENDPOINTS`: 이 설정이 지정되면 해당 이름의 endpoint만 로드됩니다. `librechat.yaml`의 [Model specs](/docs/configuration/librechat_yaml/object_structure/model_specs): 선택기를 제한하는 경우, 나열된 spec과 `modelSpecs.addedEndpoints`에 있는 항목만 접근할 수 있습니다. 그리고 공급자 자체의 키: 값이 설정되지 않은 키 기반 endpoint는 로드되지 않으므로, 설치 환경에 키(또는 `user_provided`)를 설정한 다음, Docker에서 `docker compose up -d`를 사용하여 컨테이너를 다시 생성하고 재시작하십시오. 예를 들어 AWS 자격 증명 체인을 사용하는 [Bedrock](/docs/configuration/pre_configured_ai/bedrock)과 같이 환경에서 자격 증명을 가져오는 endpoint는 키 대신 리전 설정과 작동하는 체인이 필요합니다.
- **엔드포인트는 존재하지만, 원하는 모델이 없는 경우입니다.** 목록의 출처에 따라 무엇을 확인해야 할지 결정됩니다. `user_provided` 키를 사용하는 경우, LibreChat은 제공업체에 어떤 모델이 존재하는지 물어볼 수 없으므로 내장된 목록을 제공합니다. 이 경우 [`OPENAI_MODELS`](/docs/configuration/pre_configured_ai/openai)와 같이 제공업체의 `_MODELS` 변수를 사용하여 원하는 모델을 지정해야 합니다. 실제 서버 측 키를 사용하고 `_MODELS`를 설정하지 않은 경우, 일부 제공업체는 모델 목록을 요청받으므로 제한적이거나 오류가 있는 키는 목록을 단축시킬 수 있습니다. 반면 [Google](/docs/configuration/pre_configured_ai/google)을 포함한 다른 제공업체는 목록을 가져오지 않으므로 키와 관계없이 `_MODELS`를 설정해야 합니다. 다른 설정을 변경하기 전에 [AI Setup](/docs/configuration/pre_configured_ai)에서 해당 제공업체의 페이지를 확인하십시오. Ollama나 OpenRouter와 같은 [custom endpoint](/docs/configuration/librechat_yaml/object_structure/custom_endpoint)는 `_MODELS`를 완전히 무시합니다. 이 경우 목록은 자체 `librechat.yaml` 블록의 `models.default` 및 `models.fetch`에서 가져옵니다. 또한 `librechat.yaml`에 [model specs](/docs/configuration/librechat_yaml/object_structure/model_specs)가 정의되어 있다면, 엔드포인트 자체 모델 대신 해당 목록에서 선택하게 됩니다.
- **응답이 인증 또는 잘못된 키 오류로 인해 실패합니다.** 키가 잘못되었거나, 만료되었거나, 선택한 모델에 대한 액세스 권한이 없습니다. **Set API Key** 대화 상자에서 키를 다시 입력하거나, 설치 환경에서 값을 수정한 후 재시작하세요.
