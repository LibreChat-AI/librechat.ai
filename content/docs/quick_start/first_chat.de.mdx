LibreChat ist eine Software, die Sie selbst hosten, und sie wird ohne eigenen API-Schlüssel ausgeliefert. Sobald Ihre Instanz läuft, führen Sie diese Schritte von der Anmeldeseite zu einer funktionierenden Konversation.

<Callout type="info" title="Noch nichts am Laufen?">

Installieren Sie zuerst LibreChat: [Quick Start](/docs/quick_start) für den 5-minütigen Docker-Weg, [Local Installation](/docs/local) für Docker, npm oder Helm, oder [Remote Hosting](/docs/remote), um es auf einem Server bereitzustellen.

Um LibreChat auszuprobieren, bevor Sie etwas installieren, bietet das Projekt eine kostenlose öffentliche Demo unter [chat.librechat.ai](https://chat.librechat.ai) an. Diese ist für Evaluierungszwecke gedacht, nicht für private Daten.

</Callout>

<Steps>
  <Step>

### Öffnen Sie LibreChat in Ihrem Browser [#open-librechat-in-your-browser]

Eine lokale Docker- oder npm-Installation stellt die App unter [http://localhost:3080](http://localhost:3080) bereit. Der Port stammt aus `PORT`. Falls Sie diesen geändert oder einen anderen Host-Port in der `docker-compose.override.yml` gemappt haben, verwenden Sie stattdessen diesen.

Überall sonst ist die Adresse diejenige, die Ihnen Ihre Bereitstellung vorgibt: die von Railway zugewiesene Domain, Ihre `username-projectname.hf.space`-URL auf Hugging Face, die Server-IP oder Domain vor Ihrer Remote-Docker- oder Kubernetes-Installation. `DOMAIN_CLIENT` ist eine separate Einstellung, die Adresse, die LibreChat in die von ihm generierten Links einfügt. Verweisen Sie also auf dieselbe öffentliche URL, anstatt Ihre Browser-Adresse daraus abzulesen.

Falls nichts geladen wird, siehe [If nothing loads](#if-nothing-loads) weiter unten.

  </Step>
  <Step>

### Erstellen Sie Ihr Konto [#create-your-account]

Die E-Mail-Registrierung ist standardmäßig aktiviert (`ALLOW_REGISTRATION=true`), und es gibt keine Standard-Anmeldedaten: Klicken Sie auf **Sign up** und wählen Sie Ihre eigene E-Mail-Adresse und Ihr Passwort.

Nicht jede Instanz bietet dieses Formular an. Wenn es kein **Sign up** gibt, verwenden Sie eine Anbieter-Schaltfläche, falls eine angezeigt wird, oder das Anmeldeformular, falls die Instanz die Authentifizierung über ein Verzeichnis vornimmt: Beides kann Ihr Konto bei der ersten Anmeldung erstellen. Wenn nichts davon angeboten wird oder wenn die Anmeldung verweigert wird, weil Ihr Konto nicht existiert, bitten Sie den Betreiber der Instanz um ein Konto. Welche Steuerelemente erscheinen, wird durch die [authentication settings](/docs/configuration/authentication) der Instanz bestimmt.

<Callout type="info" title="Erstes Konto = Admin bei Single-Tenant-Bereitstellungen">

In einer nicht mandantenfähigen (unscoped single-tenant) Bereitstellung wird das erste registrierte Konto zum Admin-Konto, und jedes weitere Konto erhält standardmäßig die Rolle `USER`. Mandantenfähige (tenant-scoped) Bereitstellungen stufen den ersten Benutzer in jedem Mandanten nicht automatisch hoch; richten Sie Mandantenadministratoren über einen vertrauenswürdigen administrativen Prozess ein ([Authentication](/docs/features/authentication)).

Eine OpenID-Bereitstellung kann die Standardrolle in beide Richtungen überschreiben: `OPENID_ADMIN_ROLE` stuft ein übereinstimmendes Konto zum Administrator hoch, und die generische Rollensynchronisierung (`OPENID_ROLE_SYNC_ENABLED`) bildet Anbieterrollen auf andere Nicht-Administrator-Rollen ab. Siehe [OpenID Connect](/docs/configuration/dotenv#openid-connect).

</Callout>

Wenn Sie [OAuth2/OIDC](/docs/configuration/authentication/OAuth2-OIDC) oder [SAML](/docs/configuration/authentication/SAML) konfiguriert haben, verwenden Sie die Schaltfläche des jeweiligen Anbieters anstelle des Formulars.

[LDAP/AD](/docs/configuration/authentication/ldap) fügt keine Schaltfläche hinzu. Melden Sie sich über dasselbe E-Mail- und Passwort-Formular an und geben Sie Ihren Verzeichnis-Benutzernamen anstelle der E-Mail-Adresse ein, wenn der Server `LDAP_LOGIN_USES_USERNAME=true` gesetzt hat.

  </Step>
  <Step>

### Einem Modell einen API-Schlüssel zuweisen [#give-a-model-an-api-key]

LibreChat kommuniziert mit KI-Anbietern unter Verwendung Ihrer Anmeldedaten, und `.env.example` liefert die vorkonfigurierten Anbieter als `user_provided` aus:

```bash filename=".env"
OPENAI_API_KEY=user_provided
ANTHROPIC_API_KEY=user_provided
GOOGLE_KEY=user_provided
```

Mit diesem Wert stellt jeder Benutzer seinen eigenen Schlüssel über die Web-UI bereit: Wählen Sie den endpoint aus, öffnen Sie das Zahnrad-Symbol daneben und füllen Sie den Dialog **Set API Key** aus.

Dieser Wert ist nur dann ein Standardwert, wenn die Installation von `.env.example` aus gestartet wird, was auf Docker und npm zutrifft. Ein Helm-Release, ein Railway-Service oder ein Hugging Face Space enthält nur die Variablen, die Sie selbst festlegen. Daher wird ein endpoint, für den Sie keine Anmeldedaten hinterlegt haben, gar nicht erst geladen, und es erscheint kein Dialog für den Schlüssel. Setzen Sie die Variable dort auf `user_provided`, bevor Sie erwarten, dass Benutzer ihre eigenen Schlüssel mitbringen, und starten Sie die Workload neu, damit laufende Pods oder Container diese Änderung übernehmen. Derselbe Dialog ist über **Einstellungen → Daten & Datenschutz → API-Schlüssel** erreichbar, wo Schlüssel später auch überprüft und rotiert werden können.

Wenn Sie kein Endpoint-Dropdown und kein Zahnrad-Symbol sehen, hält diese Instanz den Selektor verborgen, entweder durch [model specs](/docs/configuration/librechat_yaml/object_structure/model_specs) oder durch ihre `interface`-Einstellungen. Legen Sie Ihren ersten Schlüssel unter **Einstellungen → Daten & Datenschutz → API-Schlüssel** fest, wo die Endpoints aufgelistet sind, die für die Verwendung eines benutzerdefinierten Schlüssels konfiguriert wurden.

Um stattdessen einen Schlüssel einmalig für alle zu konfigurieren, setzen Sie den echten Schlüssel anstelle von `user_provided` ein und starten Sie LibreChat neu. Unter Docker erstellen Sie die Container mit `docker compose up -d` neu und fügen `-f ./deploy-compose.yml` hinzu, falls dies die Datei ist, von der Ihr Stack ausgeführt wird: `docker compose restart` behält die Umgebung bei, die der Container bereits hat, sodass der alte Wert erhalten bleibt. Kein Benutzer wird zur Eingabe aufgefordert und der Schlüssel verbleibt auf dem Server. Wo Sie ihn festlegen, hängt von Ihrer Installationsmethode ab: `.env` für Docker und npm, ein Kubernetes Secret für [Helm](/docs/local/helm_chart#configuration), die Dienstvariablen im Railway-Dashboard, Space Secrets auf [Hugging Face](/docs/remote/huggingface). Anbieter-spezifische Schritte finden Sie unter [AI Setup](/docs/configuration/pre_configured_ai).

<Callout type="warn" title="Ein geteilter Schlüssel auf einer öffentlichen URL kann von jedem verwendet werden">

Die Registrierung ist standardmäßig geöffnet. Auf einer Instanz, die aus dem Internet erreichbar ist, kann sich also jeder, der die URL findet, anmelden und Ihren Schlüssel belasten. Bevor Sie einen serverseitigen Schlüssel für eine öffentliche Bereitstellung konfigurieren, stellen Sie sicher, dass niemand, den Sie nicht beabsichtigt haben, ein Konto erstellen kann. Das E-Mail-Formular, jede Anbieter-Schaltfläche und jedes Verzeichnis, gegen das Sie authentifizieren, erstellen Benutzer jeweils zu ihren eigenen Bedingungen. Das Schließen einer Methode schließt also nicht alle anderen aus; [Authentication](/docs/configuration/authentication) behandelt die Einstellungen für jede einzelne. Wenn Sie die Anbieter auf `user_provided` belassen, wird das Problem vollständig vermieden.

</Callout>

<Callout type="info" title="Kein bezahlter API-Key?">

Führen Sie ein Modell auf Ihrer eigenen Hardware mit [Ollama](/docs/configuration/librechat_yaml/ai_endpoints/ollama) aus oder erreichen Sie viele Anbieter über ein Gateway wie [OpenRouter](/docs/configuration/librechat_yaml/ai_endpoints/openrouter). Beide werden als [benutzerdefinierte Endpunkte](/docs/quick_start/custom_endpoints) hinzugefügt.

</Callout>

  </Step>
  <Step>

### Senden Sie Ihre erste Nachricht [#send-your-first-message]

Wählen Sie einen endpoint und ein Modell aus der Auswahl oben im Chat, geben Sie Ihren Prompt ein und senden Sie ihn ab. Wenn die Instanz die Auswahl verbirgt, wurde diese bereits für Sie getroffen: einfach eingeben und absenden. Die Antwort wird gestreamt und die Konversation gespeichert, sodass Sie über die Seitenleiste jederzeit darauf zurückgreifen können.

  </Step>
</Steps>

## Falls nichts geladen wird [#if-nothing-loads]

Eine Seite, die niemals erscheint, ist ein Installationsproblem, und die Überprüfung hängt davon ab, wie Sie die Installation durchgeführt haben:

- **Docker.** Bestätigen Sie, dass die Container mit `docker compose ps` ausgeführt werden, und lesen Sie dann die API-Logs mit `docker compose logs api`. Auf einem Server, der mit der Anleitung [Docker on Linux](/docs/remote/docker_linux) eingerichtet wurde, läuft der Stack über eine nicht standardmäßige Compose-Datei. Verwenden Sie daher `sudo docker compose -f ./deploy-compose.yml ps` und `sudo docker compose -f ./deploy-compose.yml logs api`. Mehr dazu unter [Docker troubleshooting](/docs/local/docker#troubleshooting).
- **npm.** LibreChat läuft in dem Terminal, in dem Sie `npm run backend` gestartet haben; lesen Sie daher die Ausgabe dieses Terminals. Wenn der Prozess beendet wurde, starten Sie ihn erneut und lesen Sie die Fehlermeldung, die er ausgibt.
- **[Helm](/docs/local/helm_chart) oder eine andere Kubernetes-Installation.** Überprüfen Sie mit `kubectl get pods -n <release-namespace>`, ob die Pods ausgeführt werden, lesen Sie den API-Pod mit `kubectl logs -n <release-namespace> <pod>` aus und bestätigen Sie, dass der Service oder Ingress tatsächlich den Port freigibt, auf den Sie zugreifen. Beide Befehle verwenden standardmäßig Ihren aktuellen Namespace; eine leere Liste bedeutet daher meist, dass der falsche Namespace verwendet wird.
- **Railway oder ein anderer Host.** Öffnen Sie die Deployment-Logs im Dashboard des Anbieters (bei Railway die Schaltfläche **View logs** beim Service) und navigieren Sie zu der öffentlichen URL, die der Anbieter zugewiesen hat, anstatt `localhost` zu verwenden.

## Wenn kein Modell antwortet [#if-no-model-answers]

- **Der endpoint selbst fehlt in der Auswahl.** Drei separate Einstellungen können ihn verbergen, also überprüfen Sie jede einzelne. `ENDPOINTS` in der `.env`: Wenn diese gesetzt ist, werden nur die dort genannten endpoints überhaupt geladen. [Model specs](/docs/configuration/librechat_yaml/object_structure/model_specs) in der `librechat.yaml`: Wenn diese die Auswahl einschränken, sind nur die von Ihnen aufgelisteten specs sowie alles unter `modelSpecs.addedEndpoints` erreichbar. Und der eigene Schlüssel des Anbieters: Ein schlüsselbasierter endpoint ohne konfigurierten Wert wird nicht geladen; setzen Sie also dessen Schlüssel (oder `user_provided`) dort, wo Ihre Installation ihre Umgebungsvariablen speichert, und starten Sie dann neu, indem Sie die Container mit `docker compose up -d` auf Docker neu erstellen. Ein endpoint, der stattdessen Anmeldedaten aus seiner Umgebung bezieht, wie zum Beispiel [Bedrock](/docs/configuration/pre_configured_ai/bedrock) aus der AWS-Anmeldedatenkette, benötigt eine gesetzte Region und eine funktionierende Kette anstelle eines Schlüssels.
- **Der endpoint ist vorhanden, aber das gewünschte Modell nicht.** Woher die Liste stammt, bestimmt, was zu überprüfen ist. Bei einem `user_provided`-Schlüssel kann LibreChat den Anbieter nicht fragen, welche Modelle existieren, daher bietet es eine integrierte Liste an: Benennen Sie die gewünschten Modelle mit der `_MODELS`-Variable des Anbieters, zum Beispiel [`OPENAI_MODELS`](/docs/configuration/pre_configured_ai/openai). Bei einem echten serverseitigen Schlüssel und nicht gesetztem `_MODELS` werden einige Anbieter nach ihrer Liste gefragt, sodass ein eingeschränkter oder fehlerhafter Schlüssel diese verkürzen kann; andere, darunter [Google](/docs/configuration/pre_configured_ai/google), rufen diese nie ab und benötigen `_MODELS`, unabhängig vom Schlüssel. Überprüfen Sie die jeweilige Seite des Anbieters unter [AI Setup](/docs/configuration/pre_configured_ai), bevor Sie andere Änderungen vornehmen. Ein [custom endpoint](/docs/configuration/librechat_yaml/object_structure/custom_endpoint) wie Ollama oder OpenRouter ignoriert `_MODELS` vollständig: Die Liste stammt aus `models.default` und `models.fetch` im eigenen `librechat.yaml`-Block. Und wenn Ihre `librechat.yaml` [Model Specs](/docs/configuration/librechat_yaml/object_structure/model_specs) definiert, wählen Sie aus dieser Liste anstelle der eigenen Modelle des endpoints.
- **Die Antwort schlägt mit einem Authentifizierungs- oder ungültigen Schlüssel-Fehler fehl.** Der Schlüssel ist falsch, abgelaufen oder hat keinen Zugriff auf das ausgewählte Modell. Geben Sie ihn erneut im Dialog **Set API Key** ein oder korrigieren Sie den Wert in der Umgebung Ihrer Installation und starten Sie diese neu.
