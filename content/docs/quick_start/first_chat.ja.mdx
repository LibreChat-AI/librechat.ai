---
title: 最初のチャット
icon: MessageSquare
description: 実行中のLibreChatインスタンスを開き、アカウントを作成し、モデルのAPIキーを追加して、最初のメッセージを送信します。
---

LibreChatは自身でホストするソフトウェアであり、それ自体にはAPIキーは付属していません。インスタンスが起動したら、以下の手順でログインページから会話を開始できる状態まで進めることができます。

<Callout type="info" title="まだ何も実行されていませんか？">

まずLibreChatをインストールしてください：5分で完了するDockerでの手順は[クイックスタート](/docs/quick_start)、Docker、npm、またはHelmを使用した[ローカルインストール](/docs/local)、サーバーへのデプロイは[リモートホスティング](/docs/remote)を参照してください。

LibreChatをインストールする前に試してみたい場合は、プロジェクトの無料公開デモを [chat.librechat.ai](https://chat.librechat.ai) で利用できます。これは評価用であり、プライベートなデータ用ではありません。

</Callout>

<Steps>
  <Step>

### ブラウザでLibreChatを開く [#open-librechat-in-your-browser]

ローカルの Docker または npm インストールでは、アプリは [http://localhost:3080](http://localhost:3080) で提供されます。ポートは `PORT` から取得されます。もし変更した場合、または `docker-compose.override.yml` で別のホストポートをマッピングした場合は、そちらを使用してください。

その他の場所では、アドレスはデプロイ先から提供されるものになります。Railwayが割り当てるドメイン、Hugging Face上の `username-projectname.hf.space` URL、あるいはリモートのDockerやKubernetesインストール環境の前面にあるサーバーIPやドメインなどがこれに該当します。`DOMAIN_CLIENT` は別の設定であり、LibreChatが生成するリンク内に含めるアドレスです。そのため、ブラウザのアドレスバーから読み取るのではなく、その同じ公開URLを指定してください。

何も読み込まれない場合は、以下の [If nothing loads](#if-nothing-loads) を参照してください。

  </Step>
  <Step>

### アカウントを作成する [#create-your-account]

Email登録はデフォルトで有効になっています（`ALLOW_REGISTRATION=true`）。デフォルトの認証情報は存在しないため、**Sign up**をクリックして、任意のメールアドレスとパスワードを選択してください。

すべてのインスタンスがそのフォームを提供しているわけではありません。**Sign up** がない場合は、プロバイダーボタンが表示されていればそれを使用するか、インスタンスがディレクトリに対して認証を行う場合はログインフォームを使用してください。いずれの場合も、初回サインイン時にアカウントが作成される可能性があります。どれも提供されていない場合、またはアカウントが存在しないためにサインインが拒否された場合は、インスタンスの管理者にアカウント作成を依頼してください。どのコントロールが表示されるかは、インスタンスの [authentication settings](/docs/configuration/authentication) によって決定されます。

<Callout type="info" title="シングルテナント環境では最初のアカウントが管理者になります">

スコープなしのシングルテナントデプロイメントでは、最初に登録されたアカウントが管理者アカウントとなり、それ以降のアカウントにはデフォルトで `USER` ロールが付与されます。テナントスコープのデプロイメントでは、各テナントの最初のユーザーが自動的に昇格されることはありません。信頼された管理フロー（[Authentication](/docs/features/authentication)）を通じてテナント管理者をプロビジョニングしてください。

OpenIDのデプロイメントでは、デフォルトのロールをいずれかの方法で上書きできます。`OPENID_ADMIN_ROLE`は一致するアカウントを管理者権限に昇格させ、汎用ロール同期（`OPENID_ROLE_SYNC_ENABLED`）はプロバイダーのロールを管理者以外の他のロールにマッピングします。[OpenID Connect](/docs/configuration/dotenv#openid-connect)を参照してください。

</Callout>

[OAuth2/OIDC](/docs/configuration/authentication/OAuth2-OIDC) または [SAML](/docs/configuration/authentication/SAML) を設定した場合は、フォームの代わりにそのプロバイダーのボタンを使用してください。

[LDAP/AD](/docs/configuration/authentication/ldap) を追加してもボタンは表示されません。サーバーで `LDAP_LOGIN_USES_USERNAME=true` が設定されている場合は、メールアドレスの代わりにディレクトリのユーザー名を入力して、同じメールアドレスとパスワードのフォームからサインインしてください。

  </Step>
  <Step>

### モデルにAPIキーを付与する [#give-a-model-an-api-key]

LibreChatはあなたの認証情報を使用してAIプロバイダーと通信します。`.env.example`には、あらかじめ設定されたプロバイダーが`user_provided`として同梱されています。

```bash filename=".env"
OPENAI_API_KEY=user_provided
ANTHROPIC_API_KEY=user_provided
GOOGLE_KEY=user_provided
```

その値を使用すると、各ユーザーはWeb UIから自身のキーを提供できるようになります。エンドポイントを選択し、その横にある歯車アイコンを開いて、**Set API Key**ダイアログに入力してください。

その値は、`.env.example` からインストールを開始した場合（つまり Docker や npm の場合）にのみデフォルトとして適用されます。Helm リリース、Railway サービス、または Hugging Face Space では、設定した変数のみが保持されるため、認証情報を設定していない endpoint は一切読み込まれず、そのためのキー入力ダイアログも表示されません。ユーザー自身にキーを用意してもらうことを想定する場合は、事前に変数を `user_provided` に設定し、実行中のポッドやコンテナがそれを反映するようにワークロードを再起動してください。同じダイアログには **Settings → Data & Privacy → API keys** からもアクセスでき、ここから後でキーの確認や更新を行うことも可能です。

エンドポイントのドロップダウンや歯車アイコンが表示されない場合、そのインスタンスは [model specs](/docs/configuration/librechat_yaml/object_structure/model_specs) または `interface` 設定を通じてセレクターを非表示にしています。**設定 → データとプライバシー → APIキー** から最初のキーを設定してください。ここには、ユーザー提供のキーを受け入れるように構成されたエンドポイントが一覧表示されます。

To configure a key once for everyone instead, set the real key in place of `user_provided` and restart LibreChat. On Docker, recreate the containers with `docker compose up -d`, adding `-f ./deploy-compose.yml` if that is the file your stack runs from: `docker compose restart` keeps the environment the container already has, so the old value survives. No user is prompted, and the key stays on the server. Where you set it depends on how you installed: `.env` for Docker and npm, a Kubernetes Secret for [Helm](/docs/local/helm_chart#configuration), the service's variables in the Railway dashboard, Space Secrets on [Hugging Face](/docs/remote/huggingface). Provider-by-provider steps live in [AI Setup](/docs/configuration/pre_configured_ai).

<Callout type="warn" title="公開URL上の共有キーは誰でも使用できてしまいます">

登録はデフォルトで有効になっているため、インターネットからアクセス可能なインスタンスでは、URLを見つけた誰でもサインアップしてあなたのキーで課金できてしまいます。公開デプロイメントでサーバーサイドのキーを設定する前に、意図しないユーザーがアカウントを作成できないようにしてください。メールフォーム、各プロバイダーのボタン、および認証を行う各ディレクトリは、それぞれ独自の条件でユーザーを作成するため、1つを閉じたからといってすべてが閉じられるわけではありません。[Authentication](/docs/configuration/authentication) に各設定の背後にある仕組みが記載されています。プロバイダーを `user_provided` のままにしておけば、この問題を完全に回避できます。

</Callout>

<Callout type="info" title="有料のAPIキーをお持ちではありませんか？">

[Ollama](/docs/configuration/librechat_yaml/ai_endpoints/ollama) を使用して独自のハードウェアでモデルを実行したり、[OpenRouter](/docs/configuration/librechat_yaml/ai_endpoints/openrouter) のようなゲートウェイを通じて多くのプロバイダーにアクセスしたりできます。どちらも [カスタムエンドポイント](/docs/quick_start/custom_endpoints) として追加されます。

</Callout>

  </Step>
  <Step>

### 最初のメッセージを送信する [#send-your-first-message]

チャット上部のセレクターからendpointとモデルを選択し、プロンプトを入力して送信します。インスタンスでセレクターが非表示になっている場合は、すでに設定が完了しているため、そのまま入力して送信してください。返信がストリーミングで表示され、会話は保存されるため、サイドバーからいつでも再開できます。

  </Step>
</Steps>

## 何も読み込まれない場合 [#if-nothing-loads]

ページが表示されない場合はインストールに問題があります。確認方法はインストール方法によって異なります：

- **Docker.** `docker compose ps` を実行してコンテナが起動していることを確認し、`docker compose logs api` でAPIログを読み取ります。[Docker on Linux](/docs/remote/docker_linux) ガイドに従ってセットアップされたサーバーでは、スタックはデフォルト以外のcomposeファイルから実行されるため、`sudo docker compose -f ./deploy-compose.yml ps` および `sudo docker compose -f ./deploy-compose.yml logs api` を使用してください。詳細は [Docker troubleshooting](/docs/local/docker#troubleshooting) を参照してください。
- **npm.** LibreChatは `npm run backend` を開始したターミナルで実行されるため、そのターミナルの出力を確認してください。プロセスが終了している場合は、再度開始して表示されるエラーを確認してください。
- **[Helm](/docs/local/helm_chart) またはその他の Kubernetes インストール。** `kubectl get pods -n <release-namespace>` でポッドが実行中であることを確認し、`kubectl logs -n <release-namespace> <pod>` で API ポッドのログを読み取り、サービスまたは Ingress が実際にブラウジングしているポートを公開していることを確認してください。どちらのコマンドもデフォルトで現在のネームスペースを参照するため、リストが空の場合はネームスペースが間違っている可能性があります。
- **Railway またはその他のホスト。** プロバイダーのダッシュボードでデプロイログを開き（Railway の場合は、サービス上の **View logs** ボタン）、`localhost` ではなくプロバイダーが割り当てたパブリック URL にアクセスしてください。

## モデルが回答しない場合 [#if-no-model-answers]

- **セレクターからエンドポイント自体が消えている場合。** 3つの個別の設定が原因で非表示になっている可能性があるため、それぞれを確認してください。`.env` 内の `ENDPOINTS`: これが設定されている場合、そこに名前が記載されたエンドポイントのみが読み込まれます。`librechat.yaml` 内の [Model specs](/docs/configuration/librechat_yaml/object_structure/model_specs): これらがセレクターを制限している場合、リストに記載したスペックと `modelSpecs.addedEndpoints` にあるもののみがアクセス可能になります。そしてプロバイダー自身のキー: 値が設定されていないキーベースのエンドポイントは読み込まれないため、インストール環境でキー（または `user_provided`）を設定し、Docker 上で `docker compose up -d` を実行してコンテナを再作成し、再起動してください。環境変数から認証情報を取得するエンドポイント（例: AWS 認証情報チェーンを使用する [Bedrock](/docs/configuration/pre_configured_ai/bedrock)）の場合は、キーではなく、リージョンの設定と正常に機能するチェーンが必要です。
- **エンドポイントは存在しますが、目的のモデルが見当たりません。** リストの取得元によって、確認すべき箇所が決まります。`user_provided` キーを使用している場合、LibreChat はプロバイダーに対してどのモデルが存在するかを問い合わせることができないため、組み込みのリストを提供します。この場合、プロバイダーの `_MODELS` 変数（例: [`OPENAI_MODELS`](/docs/configuration/pre_configured_ai/openai)）を使用して、必要なモデルを指定してください。サーバーサイドのキーを使用しており、かつ `_MODELS` が設定されていない場合、一部のプロバイダーはリストを問い合わせるため、キーの制限やエラーによってリストが短縮されることがあります。一方で、[Google](/docs/configuration/pre_configured_ai/google) のように、問い合わせを行わず、キーの種類に関わらず `_MODELS` の設定を必須とするプロバイダーもあります。他の設定を変更する前に、[AI Setup](/docs/configuration/pre_configured_ai) にある各プロバイダーのページを確認してください。Ollama や OpenRouter といった [カスタムエンドポイント](/docs/configuration/librechat_yaml/object_structure/custom_endpoint) は `_MODELS` を完全に無視します。そのリストは、`librechat.yaml` 内の該当ブロックにある `models.default` および `models.fetch` から取得されます。また、`librechat.yaml` で [Model Specs](/docs/configuration/librechat_yaml/object_structure/model_specs) を定義している場合は、エンドポイント固有のモデルではなく、そのリストから選択することになります。
- **返信が認証エラーまたは無効なキーエラーで失敗する場合。** キーが間違っているか、期限切れであるか、選択したモデルへのアクセス権がありません。**Set API Key** ダイアログでキーを再入力するか、インストール環境の値を修正して再起動してください。
